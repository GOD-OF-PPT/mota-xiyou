# v31 取舍的预览、未满足条件与生效反馈

2026-10-26。依据用户“山门余香 · 留给谁”截图修正：用户选中“余香供奉”，却看不到变化，也不知道是否已经领取。

## 原因

该古炉需要 1 重心印。截图中的选择处于条件不足、仅比较的状态；点击不会发放生命或功德，确认按钮实际上不可用。旧界面同时存在四处误导：选中印章写“定”、奖励栏写“获得”、选中状态被条件短句替代、底部在不可确认时仍写“Enter 确认”。程序保护了资源，却没有帮助玩家理解发生了什么。

## 实施

- 所有取舍明确区分“未选择 / 已选待确认 / 条件不足 / 只查看奖励 / 已实际生效”。选项上写“可获得”，预览印章改为“览”，选中卡始终显示“已选中 · 尚未生效”。
- 条件不足放在主确认区，显示完整原因。余香古炉说明“尚需 1 重心印（当前 0/1）”，并明确“先到第 3 层唤醒石生心印，再回来领取”。可免费标记当前要事；不会传送、移动、送资源或跳过前置条件。
- 选中后显示从真实现有数值计算的预计变化。例如“解锁并确认后预计：功德 9 → 25”，明确当前尚未到账。缺钥匙显示所需与持有数量；生命支付显示前后余额；无法支付时不承诺负数资源。
- 不可用确认按钮使用原因文案，不再显示 Enter 提示；底部改为“当前只可比较 · 条件满足后才能确认”。此时按 Enter 会重申“本次未生效”，不调用引擎支付动作。
- 正常选择仍需明确确认。选择、切换、双击选项、Space 比较、取消、定位和行囊往返均不结算，成功确认只结算一次。
- 实际生效后回到地图，仅保留一份场景结果：“已生效：余香供奉 / 功德 18 → 34”等实际变化，另一项封存与 Z 回溯说明一并保留。结果来自确认前后引擎状态，不是复制奖励文案，也不把预览当成已得奖励。
- 契约藏室仍严格区分“定路线”和“到北匣领取”；定位契台不扣费也不领奖。

只读模块 `js/choice-feedback.js` 统一生成状态、条件、预计数值和实际回执，`js/ui.js` 负责显示与输入；`css/ui-layout.css` 负责签页安全区和预览状态。`index.html` 与新版独立试玩更新到 v31。没有修改引擎、地图、费用、奖励、心印条件或存档格式。

- `scripts/prepare_v31_fixtures.cjs`：未解锁古炉由正常新开局后 14 次安全步行取得；其他取舍来自完整合法主线的真实行动前缀。来源和哈希见 `audits/v31-fixtures/manifest.json`。
- `audits/v31-choice-feedback-browser.json`：双画境、629×678 / 1280×720 / 1440×900 / 1989×1113 和用户截图尺寸 1236×904；实际比较、缺心印、缺钥匙、免费引导、行囊返回、两种余香奖励、单次确认、实际结果、回溯、支付生命、三项取舍、北匣延后领取和断网文件直开。检查每行文字与实际框皮的安全区。
- `audits/v31-regression-campaign-regression.json`：21 组 PC 交互、合法十八层、双结局、真实资源结算、三种神通一次结算 / 跳过和存档。
- `audits/v31-study-browser.json`：六个新旧试玩入口、刷新、隔离、正式槽位保护及离线。

代表画面按原尺寸逐张复核，包含未解锁、可确认、领取后的单一结果、缺钥匙、生命支付、窄面板三项签页和另一画境。旧源文件保存在 `.backups/choice-feedback-v31-20261026/`，最终状态与源文件哈希见 `audits/v31-final.json`。
