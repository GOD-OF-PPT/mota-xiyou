# 大圣：舍利魔塔 · 当前可玩性分析与优化建议

分析日期：2026-10-23。当前基线为 v19；网络案例见 [相近游戏玩法与反馈调研](v20-similar-games-research.md)。本轮只写研究与诊断，没有修改运行时代码、地图、数值或用户存档。

## 1. 主结论

**下一轮优先把玩家的时间集中到有后果的选择，并让这些选择的收益、代价和阶段结果更容易比较。** 现有基础已经足够支持这件事：确定性战斗、有限钥匙、真实支路、三种主动神通、六件有负面代价的法器、跨层机关与回溯均已存在。

最需要验证的结构风险是：行走与回访占比高，配装和神通变化在既有通关样本中没有充分展开，长期代价的恢复手段与局部比较工具有限。它们可能让玩家从“思考怎样通关”滑向“跟随目标反复执行”。目前没有新玩家盲测，不能把这种风险写成已经测得的低乐趣或低留存。

## 2. 证据与统计口径

### 2.1 当前已具备的能力

- 十八张地图均不相同，尺寸均为 21×21；共 387 个实体、114 个敌人、19 处莲灯、8 组取舍、6 件法器。不能称为“十八层只是同一张图复制”。
- 敌人包含普通、先攻、反震、法术、重甲、余毒和首领；不能称为“没有敌人机制”。
- 百锁三契、千丝阵眼重排、弱水切换、护送开启援手侧路、终局三种准备均有真实状态与成本；不能称为“分支都是假的”。
- 精确战损、下一攻击临界、单枚可达灵晶筹算、当前目标与安全路线、点击寻路、存档、撤销/重做、双结局、两套画境和离线直开均已有实现。
- v18 的素材修复和 v19 的莲灯溢出修复是既有成果，继续纳入回归；它们不作为本轮新发现，也不证明可玩性已经充分。

依据：当前 `js/world.js`、`js/engine.js`、`js/tactics.js`、`js/journey.js`、`js/ui.js`；历史交付见 `docs/v17-player-journey-review.md`、`docs/v18-asset-cohesion-review.md`、`docs/v19-lotus-layout-review.md`。

## 3. 缺陷、风险与优化点

下表中“事实”可由当前源码或路线重放确认；“风险”是设计推论；“待测”需要真实玩家观察。优先级 P0 为下一轮首先处理，P1 为核心玩法深化，P2 为后续扩展。

|编号 / 优先级|事实与依据|对可玩性的风险|建议与可观察结果|
|---|---|---|---|
|G01 / P0：重复执行负担|两条样本移动约占 95%，大量移动重访已走格；`world.js` 的房室与连廊结构、`engine.step`、统计记录|思考结束后仍花较多时间重复走路；但是否疲劳尚待录像确认|保留已有点击寻路，优化已探索安全段的行进节奏、回庭院捷径及回访入口。到未处理敌人、封门、断口或取舍处必须停下；不自动消费资源。|
|G02 / P0：长期代价恢复不够稳妥|`engine.checkpoint` 最多保存 30 个检查点，连续普通移动会合并；`load` 清空撤销栈。已有独立手动存档，但没有按章回退列表|玩家隔层才理解失误时，可能只能依赖记得提前手动存档；“有撤销”不等于长期规划可放心尝试|为每组三层保留有限的章节起点及重大取舍前记录；恢复整份状态，不能重复领取已消费资源。清楚说明回退范围和覆盖关系。|
|G03 / P0：局部比较与跨段判断之间有缺口|`TowerTactics.growthPlans` 只比较本层可达的单枚攻击/防御灵晶；现有下一攻击临界有效，但不计算一段路线总成本|玩家知道单战战损，却难判断“为宝物先付两场战斗”是否值得；可能过度依赖外部攻略|增加玩家主动标记的短序列比较：限定已知局面、2–3 个目标，显示总战损、钥匙和补给变化。只做只读沙盘，不输出全塔最优路线，不替玩家行动。|
|G04 / P1：能力增长与后段问题变化不对称|主动神通在 3/6/9 层解锁；12 层为被动护持，15 层引出归根心钥。11 层已有很好的双驻守重排题；两样本神通类型序列相同|后九层可能较多沿用“认出图块 → 按对应技能”的执行模式|以第 8、11、14、17 层为重点，把潮位、驻守、绕战和跨层收益组合。每章展示一种新关系，并在后三层收束；至少两条真实可达的解法具有不同公开代价。无需新增技能按钮。|
|G05 / P1：法器拥有量没有转化为足够的配装比较|6 器最多同佩 2 件，效果已有权衡；行囊 `renderKit` 展示效果文本与装卸，未展示同组已标记战斗的前后总成本。两样本各只换装 2 次|玩家可能长期保持早期组合，新法器成为收集物；这尚不是其余法器弱的平衡证明|在莲灯旁对当前已拥有的组合做同一组敌情比较，展示战损、功德折损、神通费用和负面效果。不要为了制造使用次数而强迫换装。|
|G06 / P1：可恢复灵息更像路程成本|19 处莲灯免费补息；两样本总施法耗 34 灵息、踩灯补息 18 次。生命、钥匙、珠子仍有限|部分技能消耗的主要后果可能只是再走一段路，未形成新的战术取舍|保持免费补息约定，用现有灯的位置、安全归路、驻守位与公开的机会成本组织“从整装到下一次整装”的完整小段；优先移除纯往返，不以无提示限次、随机耗损补偿。|
|G07 / P1：阶段成就感需要从文案走到感知|每层已有问题、目标、结果、章节与剧情；跨层条件和后续回访仍多。资料证明接线完成，未证明玩家能复述收益|持续赶目标，刚完成的机关和选择价值没有留下记忆|保留主目标，完成一段后显示一条具体变化：接通哪座院落、保留哪把钥匙、解救谁、下次怎样利用。只在玩家要求时展开详细复盘。|
|G08 / P2：二周目的新问题不足|终局有两种结局与取舍回顾，结束统计包含楼层、舍利、击杀和生命；未见同条件本地最佳对比或独立章节挑战入口|同一流程的第二次体验可能依赖记忆和收集，而非新的推演任务|在十八层主线之外提供可选的既有章节挑战、公开起始条件与本地记录。比较生命、钥匙、功德和救援，不把击杀数作为唯一高分标准；不引入永久刷属性。|
|G09 / P2：识别成本与资源体积仍须控制|v18 材质运行时文件合计约 45.9 MiB；主界面、地图目标、战损和行囊分别承载信息。v19 修复的是一个具体跨模式缺陷|加载与信息串读可能影响投入，但本轮没有测得启动慢或低帧率|用真实设备测冷启动、全图怪物识别、从敌情到配装的视线与操作路径；数字比较留在同一操作语境。仅在数据证实瓶颈后做压缩或交互精简。|

源码定位：`js/engine.js:93`（撤销上限）、`:162`（有效配装）、`:163`（技能费用）、`:453`（主动技能）、`:481`（供奉）、`:496`（补息）、`:502`（乘云）、`:524`（撤销）、`:584`（读档）；`js/tactics.js:5`（单拾取筹算）；`js/ui.js:664`（行囊）、`:676`（法器描述）、`:729`（终局回顾）；`js/world.js:789`（房室计划）、`:1051`（每层设计问题）。行号以研究 JSON 记录的源码哈希为准。

## 4. 推荐先做的三个小闭环

### A. 首三层：缩短执行，强化第一次比较

沿用真实的灵晶成长、战损阈值、残钟取舍和第一重心印。首先区分“正在观察新信息”和“在已知路上执行”；压缩后者。让玩家能比较一组可绕守卫与宝龛收益，并用一句结果接回下一目标。利用既有补给槽位和路线，不增加新资源总量，不要求清怪。

### B. 第 8 / 11 层：用已有能力形成多解

保留弱水和双驻守的现有好题；各选一处支路深化公开代价与解法比较。评估每个法器在真实已拥有状态下对该小段的影响，优先改遭遇与目标组合，而非直接提高法器数值。至少存在两条合法通路；不能靠注入资源、传送或未取得的装备证明可玩。

### C. 第 17–18 层：让此前选择可解释

保留末问、两佩位与三相准备。将玩家已经发生的资源变化汇成简短准备清单，并允许对当前已拥有的配置比较。结局继续保留自由选择，不追加隐藏善恶值；复盘说明保住了什么、换来了什么，帮助玩家理解再玩一局的不同目标。

三个闭环通过后，再考虑章节挑战和本地记录。现有 Canvas + DOM、模拟/表现分离的架构足够承载，暂无由本次研究支持的换引擎理由。

## 5. 怎样验证“更好玩”

先招募约 6–8 名中文 PC 玩家，分为熟悉魔塔与首次接触两组；这是后续建议，本轮没有联系或招募任何人。记录初段和一处中段的录像/访谈；不把便利样本的小数量换算为整体留存率。

|要回答的问题|记录方式|建议的首轮检验目标|
|---|---|---|
|玩家能否理解首个取舍？|让玩家用自己的话说明两路收益、支付和以后用途；记录求助次数|多数参与者能在不查攻略时说明两路差别；门槛失败时先修说明和局部布局|
|疲劳来自思考还是重复执行？|标记录像中没有新信息的回跑段，并统计真实用时|与同一场景旧版相比减少约 20% 的纯执行时间，同时不自动代做任何关键决策|
|章节是否产生完成感？|结束一段后询问“你刚改变了什么，接下来想做什么”|能复述一项具体结果和一个自主目标，而非只说“继续上楼”|
|法器是否让人产生不同计划？|比较真实拥有集合，观察是否主动查看差异及其理由|出现至少两种有依据的方案；无需所有人都频繁换装|
|失败是否可理解、可恢复？|从公开代价中作一次不佳选择，再找恢复入口；测恢复用时与资源一致性|能找到正确范围的回退，说明原因；恢复不复制资源、不隐瞒此前消费|
|是否愿意再玩？|在完整一段后提供不同公开目标，询问是否愿意继续及理由|收集具体动机；本轮不预设已经提高复玩率|

“20%”“6–8 人”和分段规模均为本作拟定的探索性标准，不是竞品研究或行业规范中的固定阈值。先建立真实人类基线，再决定是否保留这些目标。

功能验收仍需独立进行：十八层合法行动、有限预算、两套画境、原存档、明确确认、场景输入隔离、跳过演出不重复结算和 `index.html` 离线直开。功能通过与玩家理解、投入、乐趣分开记录。

## 6. 建议顺序与本轮产物

1. 先观察首三层，确定纯执行负担、理解困难和恢复困难分别占多少。
2. 优先做 G01–G03：安全行进、按章恢复、有限范围比较。避免重新开发已有寻路与战损功能。
3. 再做 G04–G07：中后段组合题、配装收益和阶段结果；每次只验证一个完整小段。
4. 最后考虑 G08–G09：可选复玩目标与有测量依据的性能工作。

本轮交付为两份分析文档、网络来源记录和可复算的路线统计。没有实施上述建议，没有在用户浏览器运行新一轮试玩，也没有把先前的自动验收升级成外部玩家研究结论。
